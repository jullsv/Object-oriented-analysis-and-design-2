# Лабораторная работа №4

**Паттерн:** Фиктивная служба (Service Stub)

**Предметная область:** Магазин техники с расчетом доставки

**Описание проблемы:**
Функционирование разрабатываемого ПО «Магазин техники» требует расчета стоимости и сроков доставки заказов. 
В реальной архитектуре данная задача решается путем обращения к внешним логистическим сервисам (API служб доставки: СДЭК, Почта России, Яндекс.Доставка).
Зависимость приложения от сторонней службы создает ряд критических проблем на этапах разработки и тестирования - зависит от ресурсов, которые полностью контролируются кем-то другим,
нередко замедляет процесс разработки, заставляя разработчиков ждать,
пока служба вернется к работе.
Реальные HTTP-запросы к логистическим серверам занимают несколько секунд. Это делает отладку графического интерфейса неудобной, а автотесты – медленными и нестабильными.

**Решение:**
Система реализует паттерн Service Stub для расчёта стоимости доставки и взаимодействует с базой данных SQLite.

## Основные компоненты
- IDeliveryService (Интерфейс службы доставки) - Позволяет подменять реализацию без изменения кода.
- ShopApp - Центральный компонент системы, управляющий пользовательским интерфейсом JavaFX.
- DatabaseManager - Класс для работы с SQLite базой данных.
- Product - Модель товара в магазине.
- Order - Модель оформленного заказа.
- OrderService - Бизнес-логика обработки заказов.
  Две заглушки на выбор:
- StubDeliveryService (Фиктивная служба доставки):
  - Если города одинаковые: базовая стоимость 300 руб, 1 день
  - Если разные: 800 руб, 3 дня
  - Добавляется плата за вес: 50 руб/кг
- RealDeliveryService (Реальная служба доставки):
  - Базовая стоимость: 1000 руб
  - Плата за вес: 70 руб/кг
  - Срок доставки: 4 дня
- DeliveryResult (Результат расчёта доставки) - Класс-контейнер для результата вычислений.

## Сравнительный анализ
В реализации с паттерном Service Stub архитектура приложения строится вокруг интерфейса IDeliveryService, который определяет контракт для расчёта стоимости доставки. Этот интерфейс имеет две реализации: StubDeliveryService — упрощённая версия для тестирования и демонстрации, и RealDeliveryService — версия с более сложной логикой, имитирующая работу с реальным внешним API. Класс OrderService не знает, какая именно реализация используется, так как получает зависимость через конструктор. Это обеспечивает слабую связность между компонентами системы.
В реализации без паттерна вся логика расчёта доставки встроена непосредственно в метод calculateDelivery класса OrderService. Нет интерфейса, нет отдельных классов для разных вариантов расчёта. При создании объекта OrderService не требуется передавать дополнительные зависимости — достаточно вызвать конструктор без параметров.

Например, для перехода с тестовой версии на продакшен достаточно заменить new StubDeliveryService() на new RealDeliveryService(). Добавление третьей службы, например, интеграции со сторонним поставщиком, требует только создания нового класса, реализующего интерфейс, без изменения остальной системы.
